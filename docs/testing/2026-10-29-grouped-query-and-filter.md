# 完整分组、即时查询与科室筛选验收

## 实现范围

1. 组合粒度整组选择，组织及自定义路径仍按已发布层级选取。
2. 精确匹配的正式结果直接读取；需要聚合的区间改为源查询，趋势逐周期计算，下钻继承同一区间和筛选。
3. Redis 缓存完整操作数快照，隔离参数、版本 SQL、有效科室范围；默认 TTL 为 300 秒。源表外部更新不是强一致，修正后需更新源修订标识或等待过期。
4. 修复截图看板的科室筛选：字段目录及候选加载使用组件固定版本，筛选栏复用请求层的组织字段解析，不以字段名逐字相同作为唯一条件。

指标使用住院死亡率、入院四十八小时转科比例、住院中药费用比例；区间为一至三月、二至四月、三月。三维组合单独核对骨科的 656 行科室、主诊断、主治医生元组。医生明细没有通过求和反推科室总值。

Redis 实际检查见到 30 个条目，TTL 269 至 300 秒；单元测试另外覆盖完整快照命中、修订键隔离、权限键隔离、并发请求去重和 Redis 故障回源。

接口和浏览器证据在 `.tmp/grouped-query-20261029/`，脚本位于 `test/dashboard-grouped-*` 及 `test/dashboard-global-filter-version.browser.mjs`。浏览器图表下钻通过 ECharts 点击事件触发，不冒充真实鼠标命中测试。编辑预览未保存或发布看板，没有重算或替换正式结果。

## 验收中修复

- 新下钻接口缺少既有角色的 API 权限映射。
- 即时空结果误用正式计算缺失提示。
- 即时结果缺少格式化目标及达标状态。
- 旧下钻适配器对空汇总值抛异常。
- 源 SQL 小写维度名未统一为发布配置字段名。
- 科室筛选栏与查询层使用不同的字段匹配规则，且漏掉固定版本的字段目录。
- 科室筛选修正中的响应式变量初始化顺序问题。

部署期间发现新 SQL 迁移编号与已有 Java 迁移重复，已改为 V44。服务已恢复，并将恢复后的连接配置保存在服务器受保护的 `config/runtime.env`，避免重启依赖已经退出的进程环境。后端部署版本为 `8c55aac`，API 和 4 个 Worker 正常。
